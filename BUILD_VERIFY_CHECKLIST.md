## 4. Log triage

Read these after a test run (they are untracked — do not commit them):

- **`solstice.log`** — Solstice's own log. Look for:
  - `[AnimationHooks] doBobHurt invoked (BobHurt sig=0x...); matrix=0x... plausible=<bool>`
    - This is the Round-3 one-time diagnostic. **If `plausible=false`**, the
      `BobHurt` sig is still a false positive and ViewModel/Animations will stay
      inert (by design — no crash). **If `plausible=true`**, the matrix is real
      and the modules should start affecting the held item.
  - `spdlog::error` / `warn` lines from `MemUtils` (zero-address patch) — should
    appear **at most once** now (Round-1 warn-once fix). A repeated flood means
    the fix did not take.
- **`crash.log`** — generated by the exception handler. Any content = a crash;
  report the top stack frame.
- **`sigreport.json`** — signature scan results. Check the entries for
  `BobHurt`, `FluxSwing`, `TapSwingAnim`, `ItemInHandRenderer_render_bytepatch`,
  `Mob_getCurrentSwingDuration`: `0` / `-1` = unresolved (that feature's patches
  are no-ops). The `render_bytepatch` is the known-good anchor (resolved in RE).

### ViewModel / Animations — honest blocker
`SigManager::BobHurt` on 1.21.120 resolves to a **false positive**
(string builder at RVA `0xCE0260`), so the matrix pointer handed to
`doBobHurt` is garbage. Round 3 added a plausibility gate so the modules
**never write through garbage** (no crash, no memory corruption) and a one-time
diagnostic that reports whether the hook ever sees a real matrix.

RE located two candidates but **neither is a safe drop-in** for the existing
`doBobHurt(void* this, glm::mat4* matrix)` C++ detour:
- `GameRenderer_bobHurt` (RVA `0x2D72340`) — real function, but signature is
  `(this, mat4* out, float amount)` with the float in **xmm2** (a plain C++
  detour can't supply it), and it is the **camera/view** bob, not the held-item
  matrix → wrong semantics for ViewModel.
- `ItemInHandRenderer_applyTransform` (RVA `0x2DA7BC4`) — correct held-item
  semantics, but called with args in **non-standard registers** (`r13`/`r15`/
  `rbp`); needs a custom register-preserving asm trampoline, not a C++ detour.

**Until a proper held-item-matrix hook is wired, ViewModel/Animations will load
but have no visible effect — this is the intended safe state, not a crash.**

### Path forward for the real hook (next round)
1. Either add a register-preserving trampoline for `ItemInHandRenderer_applyTransform`
   (preserve `r13`/`r15`/`rbp`/`xmm`), or
2. Trace the held-item `glm::mat4*` at runtime from the known-good
   `ItemInHandRenderer_render_bytepatch` anchor (RVA `0x58EB4EC`) to find a
   clean 2-arg function, then point the hook there.
